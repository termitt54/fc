# Расчётное ядро FC

GDExtension `FCSimCore`, API 5. Готовая Windows x64 библиотека находится в
`addons/fc_sim_core/bin/`. Проверено с Godot 4.7.1.

Модель игрока v2: 11 общих навыков, 5 дополнительных вратарских, один характер.
Переход старых игроков выполняется в PlayerTypes.migrate_compact; библиотека
пересобирается в fc_sim_core_v5_attraction.windows.template_release.x86_64.dll.
Сборка `fc-native-5-elo-settings` учитывает выбранный режим привлекательности
и получает сохранённые настройки без повторной загрузки мира; API остаётся 5.
После обновления этой DLL перезапустите игру и редактор Godot; `reloadable=false`.
Подробности: [компактная модель](../docs/compact-player-model.md), [составы 20 и схема 3-2-2](../docs/team-model-322.md).

## Границы модулей

| C++ модуль | Расчёты |
|---|---|
| `fc_match.cpp` | Полный матч: эпизоды, удары, голы, стандарты, карточки, травмы, характер игры, замены, дополнительное время и пенальти |
| `fc_sim_core.cpp` | Производные навыки, CA, позиции, выбор основы и скамейки, фиксированная схема 3-2-2, восстановление |
| `fc_national.cpp` | Заявка сборной: позиции, форма, готовность и погрешность тренерского отбора |
| `fc_generation.cpp` | Распределение потенциала поколения, характеристики новых игроков, сезонный рост и старение |
| `fc_lifecycle.cpp` | Подгонка характеристик к целевому CA, накопление статистики, послематчевая нагрузка |
| `fc_market.cpp` | Зарплаты, стоимость, спортивные требования, принятие предложений, продление контрактов, формулы репутации |
| `fc_agents.cpp` | Индекс свободных агентов и полный массовый поиск кандидата с лимитами, позициями, резервированием местных игроков и проверкой зарплаты |
| `fc_preview.cpp` | Монте-Карло прогнозы таблиц, групп и плей-офф, оценка трансферных кандидатов |

В GDScript остаются интерфейс, расписание и запуск задач, хранение сущностей,
оформление сделок, переходы между сезонами, обращения к БД и сохранения.
Правила и транзакционные проверки связывают эти операции с C++ ядром.
Исходные реализации расчётов сохранены для автоматического сравнения и резервного режима.

`game/native_simulation.gd` загружает общие коэффициенты из текущих игровых
модулей. Настройки матчей синхронизируются по fingerprint, таблица талантов
передаётся непосредственно при рождении. Талант страны влияет на поколение;
в матче участвуют реальные игроки и атакующий или оборонительный характер команды.

## Запуск

После обновления библиотеки перезапустить запущенную игру/Godot. При первом
расчёте в Output появляется `[Simulation] C++ / fc-native-3`.
`NativeSimulation.backend()` возвращает текущий backend.

Готовая библиотека работает без установки компилятора. Для другой платформы
нужна соответствующая сборка и запись в `.gdextension`; сейчас поставляется Windows x64.
На неподдерживаемой платформе или при отключении модуля мост использует GDScript.

Для контрольного запуска в PowerShell:

```powershell
$env:FC_SIMULATION_BACKEND = 'gdscript'
# Запустить Godot/тесты из этой оболочки.
Remove-Item Env:FC_SIMULATION_BACKEND
```

## Сборка

```powershell
# Первый запуск: загрузить закреплённые зависимости и собрать.
.\tools\build_native.ps1 -Bootstrap
# Последующие сборки:
.\tools\build_native.ps1
```

Нужны Python и Git. Скрипт использует доступный Python или bundled runtime,
либо принимает `-Python PATH`. Зависимости находятся только в игнорируемом
`tools/.native-runtime`; системные настройки не изменяются.

`toolchain.lock.json` закрепляет commit godot-cpp, LLVM-MinGW и SCons.
Скрипт проверяет SHA-256 архива компилятора. В SDK явно добавляется `<cstdlib>`
для совместимости с LLVM 23. Библиотека собирается с отключёнными fast-math и
слиянием операций с плавающей точкой, чтобы сохранить исходную арифметику.

Windows блокирует загруженную DLL: перед пересборкой закрыть использующие её
процессы Godot. Автоматическая горячая перезагрузка отключена.

## Проверки

```powershell
.\tools\run_native_tests.ps1
# Тот же функциональный набор через исходный расчёт:
.\tools\run_native_tests.ps1 -ReferenceOnly
```

Тесты работают в отдельном проекте и `fc-load-benchmark` userdata.
Пользовательская база и сохранения не используются как место записи.
Тест эквивалентности сравнивает отчёты матчей, RNG, стартовые составы,
скамейки, поколения, развитие, восстановление, рынок и прогнозы.
Он включает крайние настройки и неполные команды.

`FCSimCore.metrics(reset)` показывает число нативных матчей и время подготовки,
игры и сборки отчёта. Полное время дня измеряется отдельно, включая работу
GDScript и интерфейса. Все измерения производительности:
[docs/native-simulation-performance.md](../docs/native-simulation-performance.md).

## Разработка модели

При изменении алгоритма обновляются C++ реализация и эталон GDScript,
затем запускаются тесты эквивалентности. Общие коэффициенты продолжают
задаваться в существующих игровых модулях. Изменение констант кода
применяется после перезапуска; значения редактора матчей и талантов
синхронизируются во время игры.

## Инварианты

- Порядок вызовов RNG и арифметики сохраняется. Нет второго скрытого баланса.
- Преобразование пары шансов в float32 сохраняет поведение `Vector2` исходного движка.
- Сортировки с равными оценками используют алгоритм Godot.
- Игроки имеют уникальные ID; ссылки и изменения сущностей сохраняются на границе Godot/C++.
- Сохранения имеют прежний формат. Временные данные C++ не записываются в сейв.
- Модуль вызывается в текущем потоке симуляции. При добавлении параллельных задач
  каждому worker понадобится отдельный экземпляр ядра: служебные кэши сортировки общие для экземпляра.

godot-cpp и инструментарий: [официальный репозиторий](https://github.com/godotengine/godot-cpp),
[GDExtension C++](https://docs.godotengine.org/en/stable/tutorials/scripting/gdextension/gdextension_cpp_example.html).
